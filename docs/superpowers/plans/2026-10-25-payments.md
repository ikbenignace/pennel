# Fase C — Betalen voor Pennel Cloud — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Cloud Free user upgrades to Cloud Pro from the app through Stripe Checkout, gets Pro limits within a minute through Stripe webhooks, manages the subscription in the Stripe customer portal, and falls back to Free limits when it ends. Local use never depends on any of this.

**Architecture:** The Rust server stays the only account system. It talks to Stripe with `reqwest` (form-encoded) through a small `StripeApi` trait, so routes and webhook handling are tested against a fake Stripe (an axum app on `127.0.0.1:0`, as in the proxy tests). Webhooks are verified by HMAC and stored by event id; each relevant event re-fetches the subscription and upserts its current state. `entitlements()` becomes async and reads the plan from Postgres; a pure `limits_for(plan)` holds the numbers. The core gets two URL calls and a few account fields; the desktop Account tab gets a "Abonnement" section.

**Tech Stack:** Server: Rust 2024, axum 0.8, sqlx 0.8, reqwest, `hmac` 0.12 (matching `sha2 = 0.10` in the workspace), chrono. Web: Next 16, vitest. Core: Rust, ureq 3, uniffi 0.32, mockito. Desktop: Tauri 2, TypeScript, node test runner.

## Global Constraints

- We store only Stripe ids (`cus_…`, `sub_…`, `price_…`, `evt_…`), plan, interval, status, quantity, period end and `cancel_at_period_end`. No card data, no addresses, no Stripe payloads, no invoice contents.
- Logs: method, route template, status, duration, account id, Stripe event **type** (never its id or payload). Stripe error bodies are never echoed to clients.
- A webhook without a valid `Stripe-Signature` (HMAC-SHA256 over `"{t}.{body}"`, tolerance 300 s, any `v1` match) → 400, nothing stored. A known event id → 200, nothing done.
- Plans: `free`, `pro`, `team`. Limits come only from `limits_for(plan)` (Task 1 table, spec §4.5). Beta: until `PENNEL_BETA_UNTIL` (UTC date) every account gets the current beta limits (`storage 1 GB, object 5 MB, 10 devices, 72_000 s, 2_000_000 tokens`, sync upload on).
- Grace: status `past_due` keeps the paid plan for 7 days after `past_due_since`; `unpaid`, `canceled`, `incomplete_expired` → free.
- Dutch user-facing messages exactly as written here; JSON errors `{"error","message"}` as in plan 1.
- Server: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`; web: `npm run lint && npm run typecheck && npm test && npm run build`. musli: `cd core && cargo fmt -- --check && cargo clippy --lib --tests -- -D warnings && cargo test`, `make core && make test && make app`, `cd apps/desktop && npm ci && npm run build && npm test`, `cd apps/desktop/src-tauri && cargo test`.

## Review Focus

1. `customer.subscription.updated` (status active) arrives **before** `checkout.session.completed` → the account still ends up Pro, because both handlers re-fetch the subscription and match the customer to the user through `billing_customers`. Test in Task 4.
2. The same webhook delivered twice, or two different events processed concurrently for one subscription → one row, latest Stripe state, no error. Test in Task 4.
3. A Free account after the beta uploads an object → 403 `plan_required`; it can still `GET` objects, page the feed and `DELETE` (tombstone). The core keeps pulling and reports `PlanRequired`. Tests in Tasks 1 and 8.
4. Account deletion when Stripe is down → 503 `billing`, nothing deleted; when Stripe works → subscription cancelled, customer deleted, then the user row deleted. Test in Task 5.
5. The price the app shows equals Stripe's `unit_amount` for the configured price id (no hard-coded amount in the app). Test in Task 3 (server) and Task 9 (formatting only).
